# Frame interpolation (experimental): 90 / 120 / 144 / 180 FPS

Status: **working on macOS at 120 Hz (confirmed on an M3 Pro, 2026-10-27).
Other rates are verified headless only. Off by default.**

## What it does

The game logic still runs at 59.94 Hz. ReFare draws in-between images so that
every display refresh gets its own picture: 90 Hz (Steam Deck OLED), 120 Hz
(ProMotion), 144, 165, 180, or whatever the display runs at.

The in-between images come from the GPU command stream itself, the way RT64
interpolates N64 games:

1. Every GX command the game sends during a frame is recorded as it executes.
   Display lists are inlined and indexed matrix loads (which read guest RAM)
   are converted to immediate loads of the values they produced.
2. Each transform/projection matrix load is tagged with a key: the XF
   address, a hash of the first draw that uses it, and how many times that
   pair appeared earlier in the frame.
3. At the end of the frame (the XFB copy), the frame is drawn again once for
   each in-between image. Each redraw starts from the GPU state saved at the
   start of the frame, with every matched matrix blended a fraction *t* of
   the way from the previous frame's load to this one. The GPU state is put
   back afterwards.
4. The presenter shows the images in order, one per display refresh, then the
   real frame if it falls on a refresh of its own.

### Picking the blend fractions

A running count of display refreshes per game frame (rate ÷ 59.94) decides
which refreshes fall inside each game frame, and where:

| Output | Per game frame | Images drawn per frame |
| --- | --- | --- |
| 90 Hz | alternately t=⅔, then t=⅓ + real | 1 |
| 120 Hz | t=½ + real | 1 |
| 144 Hz | 2–3 images at uneven t, real rarely on a refresh | ~2.4 |
| 180 Hz | t=⅓, ⅔ + real | 2 |

A refresh within 0.04 of a game-frame boundary counts as "the real frame".
That keeps 120 and 180 locked to exact fractions despite 59.94 vs 60.

Loads are not blended (the current frame's value is used) when:

- there is no match in the previous frame (new or culled objects);
- the rotation part changed a lot, as with a camera cut or a teleport;
- the translation jumped more than 20% of its distance from the camera,
  which happens when identical models swap draw order;
- the projection switched between perspective and orthographic, or its
  scale changed by more than 20% (an FOV snap).

The HUD uses identity/orthographic matrices that don't change, so it is
drawn exactly as in the real frame.

Frames that draw nothing with a perspective projection (menus, the results
screen, title cards) are pure 2D. They skip interpolation and are shown as
is, at 60 FPS: in-between images would only cost time and could smear
sprites that slide or swap. The stats line counts them as "2D-only frames
shown as is".

### Pacing

- **Metal with V-Sync:** the minimum display time per drawable (normally one
  60 Hz frame) is set to one output refresh, and a frame's images are
  submitted back to back. Metal spaces them, so the video thread never sleeps
  between them.
- **Everything else:** the video thread sleeps one refresh between images.
  Linux and Windows will get backend-specific pacing (Vulkan present-wait,
  DXGI waitable swap chain, and Gamescope on the Deck) when those ports
  happen.
- **Game locked to 60.00 Hz:** while interpolating, emulation speed is set to
  100.1%. The game then makes exactly 60.000 frames/s instead of 59.94, which
  matches 90/120/180 Hz displays. Without this, one image per ~8 s had to stay
  up for an extra refresh, and arrival jitter around those moments caused
  bursts of stutter. Audio pitch rises 0.1% (under 2 cents, inaudible).
  Dolphin normally switches V-Sync off at any speed other than exactly 100%;
  that check now allows ±1%. A speed you chose yourself is left alone, and
  100% is restored when interpolation turns off.
- The first image goes out at whichever is later: the frame's slot or now.
  Frames reach the presenter ~13 ms after their slot with the extra draws.
  Only when more than 2.5 frames behind are the in-between images skipped.

### Costs and known limits

- **One display refresh of extra latency** (8.3 ms at 120 Hz, 11.1 ms at 90,
  5.6 ms at 180).
- Each in-between image is a full redraw: 90 and 120 Hz draw each game frame
  about twice, 180 Hz three times, 144 Hz about 3.4 times.
- Only geometry moved by matrices is smoothed. Anything the game animates on
  the CPU by rewriting vertex data, plus texture animation and particles
  written as raw vertices, steps at 60 Hz.
- "Match display" uses the screen's maximum refresh rate (macOS:
  `NSScreen.maximumFramesPerSecond`, re-read about twice a second). Other
  platforms report "unknown" for now and fall back to 120.
- A fixed rate above the display's refresh is capped to the display rate.
- Savestate loads and changing the setting reset the history, giving one
  frame without interpolation.

## How to enable

The L1 / Tab menu row **"Interpolation (experimental)"** cycles through Off →
Match display → 90 → 120 → 144 → 180 FPS. It takes effect on the next frame
and is saved to `build/user/Config/GFX.ini`:

```ini
[Enhancements]
RefareFrameInterpolation = True
RefareInterpolationTarget = 0   ; 0 = match display, else Hz
```

Set `REFARE_INTERP_STATS=1` to print a report every ~10 s:

- `interpolation:` the output rate, matrix loads matched and blended.
- `presenter:` swaps, sets ready, shown, dropped as late, and arrival lateness.
- `video thread:` images drawn per game frame and the time spent drawing them.
- `on glass:` (Metal) when images actually appeared. It counts intervals of
  one refresh ("on time"), images held up an extra refresh (visible hitches),
  "early" (under half a refresh) and images never shown, plus the worst gap
  and the game's frame rate (60.000 when locked).

## Testing

```sh
REFARE_INTERP_STATS=1 make run GAME=Crazy-Taxi-USA JOBS=8 \
  RUN_ARGS="--graphics Metal --user-dir build/user" 2>&1 | tee build/logs/120fps.log
```

- With "Match display" on the built-in screen, the Metal HUD should read ~120.
- In the `on glass` line, "held extra refresh" should be near zero (a few per
  minute at most) at 120 Hz. Before the 60.00 Hz lock it was at least ~7 a
  minute, in bursts.
- Picking 90 FPS on the Mac should read ~90 and look evenly paced. That
  probably needs fullscreen: a 90 Hz cadence on a 120 Hz panel only works
  where macOS can vary the refresh rate. That is a
  stand-in for the Steam Deck OLED cadence.
- Watch for ghosting (a mismatched blend), flicker on the HUD, shadows or sky,
  and judder.
- If anything breaks, set `RefareFrameInterpolation = False` in `GFX.ini`.
  That setting is the only thing that turns this code on.

## Files

- `patches/recompcore-frame-interpolation.patch` (RecompCore / Dolphin):
  - `VideoCommon/RefareFrameInterpolation.{h,cpp}` holds the recorder, the
    matcher/blender and the replay.
  - `OpcodeDecoding.cpp` feeds every executed command to the recorder.
  - `BPStructs.cpp` handles the frame start/end at the XFB copy.
  - `Present.cpp/.h` presents the in-between frame before the real one.
  - `VideoState.cpp` resets on savestate load.
  - `GraphicsSettings` adds `GFX_REFARE_FRAME_INTERPOLATION`.
- `src/refare_options.cpp` holds the menu row; `src/refare_metal_hud.mm` detects the display refresh rate. `tests/options_test.cpp` covers it.

## Android APK — scoping (research only)

An APK is not buildable from this workspace tonight: the Android SDK and NDK
download servers are blocked by its network allowlist. Even with them, it is
a multi-session project rather than a rebuild. What it would take:

- **Engine:** RecompCore is Dolphin, which already has a complete Android
  port in the tree (`Source/Android`, with the Kotlin app, JNI bridge,
  Vulkan/GLES backends and the ARM64 JIT for the fallback path). The
  Vulkan backend would replace Metal.
- **Game code:** the recompiled C output has to be compiled with the NDK for
  `arm64-v8a`. It would be loaded as a `.so` from the APK's native library
  folder instead of the macOS `.dylib`. DolRecomp's output is
  plain C, so this is mostly a toolchain/CMake job.
- **Frontend:** the ModernGekko launcher/runner is desktop SDL. Android needs
  either SDL3's Android activity template or a slimmed Dolphin Android shell
  for touch/controller input, the surface and lifecycle (pause/resume).
- **ReFare features to port or disable:**
  - The Metal HUD, the macOS focus/Spotlight handling and the Metal
    presentation hooks are macOS-only.
  - The options overlay (ImGui), widescreen culling, sprite clamp and
    interpolation are portable.
- **Game data:** the APK cannot contain Crazy Taxi's files. It would ask
  for the user's own disc image on first run and extract it on the device, the
  way the desktop build uses your dump.
- **Rough plan:**
  1. Cross-compile the module and RecompCore with the NDK.
  2. Boot headless on a device over adb.
  3. Add the Vulkan surface, input and audio.
  4. Package it, then tune performance (Snapdragon 8-class devices should run
     it; the replay for 120 FPS would be a later step).
