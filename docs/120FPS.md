# 120 FPS (experimental frame interpolation)

Status: **prototype, off by default, not yet seen on screen.**

Verified in a Linux build with the headless Null video backend:

- All patches still apply cleanly and reverse-check.
- The L1 options test passes with the new row.
- A 260 s automated run (title → gameplay driving → back) recorded and
  replayed 9,000 frames without a crash. Frame streams ran 3–265 KB, and
  94–96% of matrix loads matched the previous frame (93–95% blended).

Not verified: anything visual. The Null backend draws nothing, and there is
no Metal here. The first real look is your Mac.

## What it does

The game logic still runs at 59.94 Hz. ReFare draws one extra in-between image
per frame, so a 120 Hz display (ProMotion MacBook Pro, 120 Hz monitor) gets
~119.88 presents per second.

The in-between frame comes from the GPU command stream itself, the way RT64
interpolates N64 games:

1. Every GX command the game sends during a frame is recorded as it executes.
   Display lists are inlined and indexed matrix loads (which read guest RAM)
   are converted to immediate loads of the values they produced.
2. Each transform/projection matrix load is tagged with a key: the XF
   address, a hash of the first draw that uses it, and how many times that
   pair appeared earlier in the frame.
3. At the end of the frame (the XFB copy), the GPU state is rewound to the
   start of the frame. The frame is drawn again with every matched matrix
   blended halfway toward the previous frame's matching load. That image is
   saved, and the GPU state is put back.
4. The presenter shows the in-between image in the frame's normal slot and
   the real frame 8.34 ms later.

Loads are not blended (the current frame's value is used) when:

- there is no match in the previous frame (new or culled objects);
- the rotation part changed a lot, as with a camera cut or a teleport;
- the translation jumped more than 20% of its distance from the camera,
  which happens when identical models swap draw order;
- the projection switched between perspective and orthographic, or its
  scale changed by more than 20% (an FOV snap).

The HUD uses identity/orthographic matrices that don't change, so it is
drawn exactly as in the real frame.

### Costs and known limits

- **One 120 Hz frame (~8.3 ms) of extra input latency.** This is inherent to
  showing a frame that sits *between* two real frames.
- The video thread renders each frame twice, so GPU and video-thread load
  roughly doubles.
- Only geometry moved by matrices is smoothed. Anything the game animates on
  the CPU by rewriting vertex data, plus texture animation and particles
  written as raw vertices, steps at 60 Hz.
- If the in-between frame would be more than 4 ms late, it is dropped and the
  real frame is shown alone. Under load this degrades back to 60 FPS rather
  than delaying the game.
- On a 60 Hz display it can't help (two presents per refresh) and only adds
  latency, so leave it off there.
- Savestate loads and toggling the setting reset the history, giving one
  frame without interpolation.

## How to enable

The L1 / Tab menu has a new row, **"120 FPS (experimental)"**, between FXAA
and Metal HUD. It takes effect on the next frame and is saved to
`build/user/Config/GFX.ini` as:

```ini
[Enhancements]
RefareFrameInterpolation = True
```

Set `REFARE_INTERP_STATS=1` in the environment to print a line every ~10 s
showing how many matrix loads matched and how many were blended.

## Morning test plan (macOS)

```sh
git fetch . refare/120fps   # if the branch is not already local
git switch refare/120fps
make            # re-applies patches, including recompcore-frame-interpolation
REFARE_INTERP_STATS=1 make run
```

1. Play as normal and turn on L1 (or Tab) → "120 FPS (experimental)".
2. Turn on the Metal HUD. It should report ~120 FPS on the built-in display.
3. Drive in a straight line, then in tight turns. Watch for:
   - ghosting or "double" objects (a mismatched blend);
   - cars or pedestrians snapping (no match, so not blended; acceptable);
   - flicker in the HUD, menus, shadows or the sky;
   - anything that looks wrong only every other refresh.
4. Check the stats line: "matched" should sit well above 80% during driving.
5. Turn it off again to compare feel and latency.
6. If anything breaks, record a pacing capture as before. I can also trace a
   frame (`trace-request`), and replayed draws will show up in the trace.

If the game crashes, or the screen goes black or garbled, turn the setting
off in `GFX.ini` (`RefareFrameInterpolation = False`) and tell me. The
setting is the only thing that turns this code on.

## Files

- `patches/recompcore-frame-interpolation.patch` (RecompCore / Dolphin):
  - `VideoCommon/RefareFrameInterpolation.{h,cpp}` holds the recorder, the
    matcher/blender and the replay.
  - `OpcodeDecoding.cpp` feeds every executed command to the recorder.
  - `BPStructs.cpp` handles the frame start/end at the XFB copy.
  - `Present.cpp/.h` presents the in-between frame before the real one.
  - `VideoState.cpp` resets on savestate load.
  - `GraphicsSettings` adds `GFX_REFARE_FRAME_INTERPOLATION`.
- `src/refare_options.cpp` holds the menu row. `tests/options_test.cpp` covers it.

## Android APK — scoping (research only)

An APK is not buildable from this workspace tonight: the Android SDK and NDK
download servers are blocked by its network allowlist. Even with them, it is
a multi-session project rather than a rebuild. What it would take:

- **Engine:** RecompCore is Dolphin, which already has a complete Android
  port in the tree (`Source/Android`, with the Kotlin app, JNI bridge,
  Vulkan/GLES backends and the ARM64 JIT for the fallback path). The
  Vulkan backend would replace Metal.
- **Game code:** the recompiled C output has to be compiled with the NDK for
  `arm64-v8a`. It would be loaded as a `.so` from the APK's native library
  folder instead of the macOS `.dylib`. DolRecomp's output is
  plain C, so this is mostly a toolchain/CMake job.
- **Frontend:** the ModernGekko launcher/runner is desktop SDL. Android needs
  either SDL3's Android activity template or a slimmed Dolphin Android shell
  for touch/controller input, the surface and lifecycle (pause/resume).
- **ReFare features to port or disable:**
  - The Metal HUD, the macOS focus/Spotlight handling and the Metal
    presentation hooks are macOS-only.
  - The options overlay (ImGui), widescreen culling, sprite clamp and
    interpolation are portable.
- **Game data:** the APK cannot contain Crazy Taxi's files. It would ask
  for the user's own disc image on first run and extract it on the device, the
  way the desktop build uses your dump.
- **Rough plan:**
  1. Cross-compile the module and RecompCore with the NDK.
  2. Boot headless on a device over adb.
  3. Add the Vulkan surface, input and audio.
  4. Package it, then tune performance (Snapdragon 8-class devices should run
     it; the replay for 120 FPS would be a later step).
